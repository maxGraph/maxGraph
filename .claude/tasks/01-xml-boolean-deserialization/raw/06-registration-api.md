# Raw exploration 6 (plan step): feasibility and cost of a boolean key registration API

## Existing extension point patterns

Style/shape registries, all the same shape: a module-level singleton of a `@private` class typed by an interface,
with the mutating entry point re-exposed as free `register*` / `unregisterAll*` functions.
- `BaseRegistry<V>` `internal/BaseRegistry.ts:8`, a Map, `@private`, `clear()`, NOT exported from index.ts.
- `Registry<V>` interface `types.ts:1606` (add/get/getName/clear), exported.
- `ShapeRegistry` (view/shape/ShapeRegistry.ts:31, index.ts:120), `StencilShapeRegistry`
  (stencil/StencilShapeRegistry.ts:28), `PerimeterRegistry` (perimeter/PerimeterRegistry.ts:11, index.ts:210),
  `EdgeMarkerRegistry` (marker/EdgeMarkerRegistry.ts:44), `EdgeStyleRegistry` (edge/EdgeStyleRegistry.ts:61, with 3
  side Maps for metadata).
- Free functions in `view/style/register.ts` (registerDefaultEdgeStyles :149, registerDefaultPerimeters :173,
  unregisterAllEdgeStyles :212, ...), `view/shape/register-shapes.ts:45,80`, `view/register-style-elements.ts:42`.
- Convention (types.ts:1613-1617): `clear()` is `@private` with "should not be called directly, call the related
  global unregister function instead". Registry object public for `add`, teardown only via the free function.

`CodecRegistry` (serialization/CodecRegistry.ts:32) is the odd one out: static members only, no `clear()`, reset via
`unregisterAllCodecs` (register-other-codecs.ts:141). Documented as legacy-shaped, nothing new follows it.

Config objects: a plain mutable object literal plus a `reset*` arrow using `shallowCopy` of a module-private snapshot.
`GlobalConfig` / `resetGlobalConfig` (util/config.ts:29,77), `StyleDefaultsConfig` / reset (:88,182),
`EntityRelationConnectorConfig`, `OrthogonalConnectorConfig`, `ManhattanConnectorConfig` (view/style/config.ts:13,42,121),
`EdgeHandlerConfig`, `HandleConfig`, `VertexHandlerConfig` (view/handler/config.ts:128,175,232),
`TranslationsConfig` (i18n/config.ts:60). All `@experimental @category Configuration`, all exported by `export *`.

Per-codec static config: `ObjectCodec.allowEval` (:236), overridden in `StylesheetCodec` (:46) and
`EditorToolbarCodec`. Mutable static, no reset, predates the config-object convention.

**The precedent for exactly this artifact** is module-private and NOT registrable: `ObjectCodec.ts:28-34`
`geometryNumericAttributes` / `pointNumericAttributes`, `Array<keyof T>`, consumed at `isNumericAttribute` (:601-602).
A boolean style key list is the same artifact one level up.

## Which pattern to imitate, if any

The `*Config` object plus `reset*Config` pair, NOT `BaseRegistry`: `Registry<V>` mandates `get(name)` and
`getName(value)`, both meaningless for a set of keys with no values, and it would be the first registry in the
codebase whose `getName` is dead code. `ManhattanConnectorConfig.startDirections: DirectionValue[]`
(view/style/config.ts:100,124) is already a config field holding a mutable array of style-domain string literals with
a reset function, the exact same data shape. Naming from the registry family (`register*` / `unregisterAll*`), storage
and reset from the config family.

## The three options priced

Baseline common to all (the fix itself): types.ts (the `BooleanCellStateStyleKeys` twin next to
`NumericCellStateStyleKeys` at :980), one new internal module with the 35-key const, codec/mxGraph/utils.ts,
codec/StylesheetCodec.ts, the two test files, CHANGELOG. **6 files + changelog.**

(a) NO API, documented limitation. Baseline only, plus 3 to 5 doc lines. Best homes:
`packages/website/docs/usage/codecs.md` (has a `## Troubleshooting` at :140, and an mxGraph import section at :99) or
`migrate-from-mxgraph.md:521` which already discusses CellStateStyle conversion. `known-issues.md` exists but is an
abandoned stub. Repo `docs/` holds ONLY `docs/adr/`, so nothing goes there except an ADR.
0 public runtime names, 1 optional type. Zero cost to users who do not need it. Cost to the user who does: their
augmented boolean decodes as 1, and `convertStyleFromString` is not exported, so the mxGraph path cannot be
intercepted without replacing `mxCellCodec` entirely.

(b) MINIMAL API, `registerBooleanStyleKeys(...keys)` + `unregisterAllCustomBooleanStyleKeys()`, appended to
`view/style/config.ts` which is ALREADY re-exported (`index.ts:205`), so no index.ts edit. Baseline + that file + one
~60-line test (model: `__tests__/util/config.test.ts` 62 lines, or `__tests__/internal/BaseRegistry.test.ts` 72 lines)
+ a subsection in `website/docs/usage/global-configuration.md` under `## Styles` (:53-105, already lists the five
registries). Sidebar is autogenerated (`sidebars.ts:14`), no wiring needed. **8 to 9 files, 2 functions, 1 type.**
The `unregisterAll` is not garnish: every reset function in this codebase exists because global mutable state leaks
between tests.

(c) RICHER. Per-codec static (mirroring `allowEval`) CANNOT reach `convertStyleFromString`, which is a free function
in `codec/mxGraph/utils.ts:6`, not a codec class, so it would need a second differently-shaped knob and no reset, and
it revives the pattern the config objects replaced. Full metadata registry (key -> 'boolean'|'number'|'string') is
~15 files and 5+ public names, threading into `ObjectCodec.isNumericAttribute` too.
THE DECISIVE OBJECTION is behavioral: if the 35 BUILT-IN keys are registered at runtime, anyone who does not call the
register function silently loses correct boolean decoding. That reproduces the `Graph` versus `BaseGraph` footgun
documented in `website/docs/usage/global-configuration.md:64-67` and `tree-shaking.md:189-202`, making XML decoding
correctness depend on which graph class was constructed. So the built-in list must stay a plain const under EVERY
option, and a registry can only ever be an additive second lookup.

## Tree shaking and the project constraints

`coding-practices.md` has no tree-shaking section; the relevant constraints are zero runtime dependencies (satisfied),
`isNullish` for nullish checks (directly relevant, the StylesheetCodec.ts:176 guard must become `!isNullish(value)`),
explicit return types on exported functions, `.js` import extensions.
`bundle-size-budgets.md` governs only the example packages: it does not forbid growth but requires updating the limit
in the same commit with a justification. Countable extra cost if the bundles grow.
The existing registries ARE tree-shakeable by design (empty registry per module, built-ins in separate modules, only
pulled in by a register call). Consequence for us: the 35-key list must be a plain const imported directly by the two
codec modules, so it is bundled only when a codec that needs it is bundled. An app that never decodes XML pays
nothing under (a) or (b).

## Prior art

- `docs/adr/` (0001 mixins, 0002 plugins, 0003 AbstractGraph, README) says NOTHING about style property
  extensibility. The README conventions (record what was rejected and why, Status field, one decision per file,
  sequential numbering) make ADR-0004 the natural place to record a "no API for now" decision.
- `CHANGELOG.md:37-58`, from `67bdd9c9e`, is the only statement of position: module augmentation is presented as a
  purely TYPE-LEVEL affordance ("applications can now declare their own style properties instead of casting"), with
  no runtime contract and no mention of serialization.
- `packages/ts-support/src/module-augmentation.ts` demonstrates it with `myCustomStyleProperty?: NUMBER`, and the
  package is a tsc-only compile check pinned to typescript 3.9.10. There is no runtime test of an augmented property
  anywhere in the tree.
- No website page covers custom style properties; grepping `website/docs/` for `augment` returns nothing. Option (b)
  would introduce the project's first user-facing claim that custom style properties have a runtime dimension.

## Recommendation

Ship the fix with NO new public API (option a) and record the decision as ADR-0004.
6 files + CHANGELOG + 1 ADR, 0 public runtime names, 1 optional type.
Reasons in order of weight: the feature has no demonstrated user (augmentation is one release old, type-level only,
validated by a tsc check on a number property); the codebase's own precedent for this artifact is a module-private
const array that never needed an API; a registry holding the built-ins would recreate the Graph/BaseGraph footgun for
XML correctness; and adding (b) later is genuinely non-breaking and cheap, 8 to 9 files of which 3 are already touched.

## TWO TRAPS TO CARRY INTO THE PLAN

1. `StylesheetCodec.ts:176` `if (value)` drops `false` too, so it stays broken after the fix unless changed to
   `!isNullish(value)`.
2. The mapped type MUST be written `NonNullable<CellStateStyle[k]> extends boolean`, not
   `CellStateStyle[k] extends boolean | undefined`, otherwise it silently OMITS `orthogonal?: boolean | null` and the
   compile-time exhaustiveness guarantee is false.
